# Example: Agent OS / Agent Marketplace

## Context

- Customer / segment: operator managing repeated business workflows.
- Persona: founder, department head, or operations lead.
- Workflow owned: coordinating recurring tasks across people, tools, and customer channels.
- Product / agent / feature being considered: Agent OS with many digital employees or an Agent Marketplace.
- Current phase: Phase 1 Need.

## Evidence

### Verified Facts

- The product idea includes multiple specialized agents.
- Users may discover or install agents from a marketplace.

### Reasonable Hypotheses

- A marketplace is valuable only after users have a specific workflow pain or growth need.
- Too many agents shown too early may feel abstract or create decision fatigue.

### Unknowns

- Which manual workflow is most painful for the target persona.
- What event makes the current workflow insufficient.
- What trust condition makes a user willing to delegate work to an agent.

## Phase 1: Need

- Current context/status quo: the user coordinates work manually across chats, docs, spreadsheets, calendars, and customer channels.
- Current workaround: personal reminders, manual checking, ad hoc delegation, copying information between tools.
- Trigger: volume, urgency, or complexity grows so manual coordination becomes unreliable.
- Pain/cost/risk/friction: missed follow-ups, slow responses, duplicated work, context loss, unclear ownership.
- Desired progress: recurring work happens reliably with less manual coordination and clear human control.
- Customer Value: important operational tasks are handled on time with less context switching and fewer misses.
- Observable signal/metric: tasks completed without manual prompting, missed follow-ups reduced, time saved, human approvals handled correctly.

## Phase 2: Action

- Alternatives the customer may research: hire an assistant, use automation tools, use CRM/project-management reminders, outsource operations.
- Comparison criteria: reliability, control, setup effort, integration coverage, privacy, cost, reversibility.
- Trust conditions: clear permissions, visible logs, approval gates, easy pause/rollback, predictable behavior.
- Anxiety or switching risks: agent sends wrong messages, leaks context, interrupts customers, or creates hidden work.
- Adoption conditions: start with one workflow, narrow permissions, observable logs, human approval for external actions.
- Smallest safe trial: install one agent for one recurring internal workflow before customer-facing work.

## Phase 3: Result

- Observed outcome vs old way: compare missed tasks, manual checking time, escalation quality, and user confidence.
- Signals/evidence: repeated successful runs, correct approvals, fewer reminders needed, user keeps the agent enabled.
- Missing evidence: whether users expand beyond the first workflow.
- Expand/adopt/iterate/stop: expand when the first workflow becomes trusted baseline; stop if reliability or control is not trusted.
- New baseline after adoption: the agent-enabled workflow becomes normal operations.
- Next Customer Value loop: marketplace discovery can matter after the user asks, "what else can I delegate?"

## Capability Implications

- Business outcome: more efficient operations or better customer responsiveness.
- Customer Value: less manual coordination and fewer missed operational tasks.
- Product/agent capability: install, configure, monitor, approve, pause, and extend agents.
- Mechanism: agent templates, permissions, connectors, schedules, logs, and approval gates.
- Next discovery questions: which workflow should be first, what permissions are acceptable, and what result would prove trust.
- Next action: interview around one real manual workflow before designing marketplace browsing.
